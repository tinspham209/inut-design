# Design

## Context

See [proposal.md](./proposal.md) for motivation. The baseline after `harden-worker-blog-and-remove-unused-apis` and `optimize-cloudflare-assets-and-cdn-cache` is:

- Canonical base64 for 10 MiB of decoded data reproduced a `RangeError` in the decoder's regex on Node, before the decoder's `try`. Worker behavior at that size has not been measured. Both handlers add a full-size copy before constructing a `Blob`, and the browser request guard reserializes and UTF-8-encodes the full parsed JSON.
- The phone route has a local IP resolver. The shared resolver today prefers `x-forwarded-for`, then the socket address, then `cf-connecting-ip`; just swapping helpers does not establish the needed behavior when those values coexist.
- SPX is an authenticated POST, with unbounded draft discovery followed by an eligible query capped at 26 and a 409 overflow at 26. The accepted 25-order case can cost `2 discovery + 25 SPX + 25 patch = 52` external requests even before drafts, retries, or alerts. Cloudflare counts redirects as additional subrequests; concurrency and wall-clock timeouts are not subrequest limits.
- The inspected local build had 699 cached `.pages` entries containing the print-only Roboto link without `onload`, and about 5.4 MiB of JS and 16.6 MiB of maps on disk under the Worker `bundle/` (no maps found under public `assets/`). These are local artifact figures, not deployed transfer sizes or Worker memory measurements. Both builders already have `dynamic(..., { ssr: false })` boundaries even though Three.js/OrbitControls still appear in the server output.

## Goals / Non-Goals

**Goals:** Improve measured upload resource use without relaxing request guards; guarantee a bounded SPX run with durable progress; correct font rendering on both delivery paths; preserve release gates and diagnose bundle cost before changing it.

**Non-Goals:** A new upload protocol or storage service, a global rate limiter rewrite, native Cron Triggers, new paid services/bindings, cache routing or TTL changes, redesigning typography, or deploying to production as part of this change.

## Decisions

1. **Validate canonical base64 in bounded stack space.** Replace the repeated-group regex and re-encoding check in `decodeBase64Image` with linear validation (nonempty, standard alphabet, quartet length, final padding and unused bits zero), then decode directly to an exact byte view using a native decoder verified on supported Node and workerd. A permissive decoder such as `Buffer.from(data, "base64")` is not validation by itself. Pass only the decoded byte range into the `Blob`, honoring the view offset and length without a redundant app-level `copy.set`; do not assume Blob or the SDK never copies. Preserve `INVALID_BASE64` internally. In the general Sanity route, separate client decode errors (400) from persistence errors (500). Do not apply the keychain 10 MiB decoded cap or the keychain format/dimension checks to the general route. Preserve the 14 MiB body cap and existing method, origin, content-type and rate-limit guards.
2. **Measure the whole upload path, not just decode speed.** Use synthetic images and mocked persistence on the current and changed builds for typical and near-limit uploads. Include body parsing, the guard, decoding and Blob construction; compare CPU and peak memory where measurable, and label wall time or Node metrics as proxies. If request-guard reserialization remains a material cost, remove it only on upload paths where the installed Next and Vinext parsers demonstrably enforce the actual body byte limit, including requests without a trusted length header. Keep the existing guard for other routes. The [Workers Free CPU and memory figures](https://developers.cloudflare.com/workers/platform/limits/) are limits, not conclusions from a Node microbenchmark.
3. **Use Cloudflare's connecting IP on the Worker phone path.** Reuse `getRequestRateLimitToken` with a Worker-specific choice grounded in the request adapter/ingress; prefer the platform-provided IP over a forwarded or socket value for this route. Do not treat a Cloudflare-looking header as authoritative on a direct Next origin. Preserve phone's `x-forwarded-for`/socket/`unknown` fallback outside Worker ingress, limiter threshold and advisory response. Keep existing callers of the shared helper unchanged. Test actual adapter behavior as well as a mocked handler.
4. **Reserve a hard SPX budget across both phases.** Use a ceiling of 45 external attempts, five below the [Workers Free limit](https://developers.cloudflare.com/workers/platform/limits/#subrequests). Reserve up to seven attempts for two discovery queries, checkpoint read/init/write, and two Telegram attempts. Bound the initial batch to eight draft publishes (one atomic Sanity transaction each) and ten tracking orders (two SPX attempts plus one Sanity patch each): `7 + 8 + 10 * 3 = 45`. Fetch at most batch size plus one per phase and do not process the lookahead row. If the measured transport makes more requests than assumed, revise the cap downward, not the ceiling. Count or prevent extra redirect hops and make the budget apply before dispatch rather than after a response. Use a cron-specific Sanity client or request path with built-in retries disabled (installed client defaults to five); verify actual adapter retry/redirect behavior for all three dependencies, and do not change unrelated consumers. Retain the existing response deadline, revision guards, draft-before-tracking phase order and concurrency limits. A deadline that prevents starting an item defers it; failures from attempted work keep their existing status precedence.
5. **Rotate the backlog with a private Sanity checkpoint.** Track a separate keyset cursor for drafts and eligible orders, ordered by `(_createdAt, _id)` and bounded by a fixed creation-time cutoff per sweep. Advance through the contiguous prefix actually attempted (including failed or unchanged attempts); never advance across an untouched row. Persist progress in one internal authenticated Sanity document, using a revision-guarded update; never expose cursor IDs or tokens in responses or logs. Wrap a completed sweep on a later tick to keep checking in-transit orders and retrying unresolved drafts; no extra unbudgeted discovery for a wrap. Use checkpoint persistence even when a batch has reportable per-item failures, and treat a failed checkpoint as a Sanity failure rather than claiming saved progress. The scheduler calls once per configured interval without overlap; revision conflicts must not overwrite progress or remove an order's existing mutation guards. Avoid stateless oldest-first slices, which would repeatedly select persistent in-transit orders, and avoid moving cursor state to the external caller.
6. **Keep the scheduler contract explicit.** Keep authenticated POST with `x-cron-secret`, `Allow: POST` on method rejection, existing failure precedence and summary fields. Return additive `hasMore` on batch summaries when discovery or the deadline indicates work deferred in the current sweep; it is not an exact global backlog count. Deferred items are not failures and do not trigger alerts by themselves. A successful partial batch is 200 instead of 409. Document this and the normal tick cadence, timeout expectations, monitor handling of 500/502, and coordinated rollback. Confirm the external caller's cadence and ability to consume the new response before any separately approved live rollout; do not infer a provider from repo files.
7. **Use a standard screen stylesheet in `_document.tsx`.** Keep the font URLs, requested weights, `display=swap`, preconnects and existing Material Icons behavior. Remove the Roboto print/onLoad/noscript workaround and its redundant same-URL preload if the stylesheet is discovered at the same point in the document. Use a standard stylesheet rather than an inline activation script so the font works without hydration and with JavaScript disabled. Check fresh prerender output and a runtime SSR page; confirm actual rendered font faces for representative Vietnamese text, not just a declared CSS family or successful request. Record the first-paint effect under identical browser conditions.
8. **Separate bundle diagnosis from trimming.** Use the current Cloudflare manifest and installed `cf` prebuilt loader to distinguish runtime modules from diagnostic maps and public `assets/`; the loader handles maps separately from runtime modules, so on-disk map bytes alone do not prove upload cost, exposure, or isolate memory. Compare raw and compressed runtime module sizes on comparable builds and trace the eager versus lazy imports of the Three.js/OrbitControls chunks. `ssr: false` is already in place and does not prove a module is absent from deployable output. Only land a measured, isolated trim; otherwise record the no-change result. Do not disable map generation speculatively: `check-worker-graph.mjs` uses `.map` `sourcesContent` to detect otherwise-hidden imports. Any change must keep equivalent coverage with negative fixtures and preserve browser behavior for both builders.

## Risks / Trade-offs

- Full JSON upload buffering can still dominate Worker CPU or memory → report end-to-end results and any unresolved Free-plan risk; do not infer safety from a decoder-only improvement or weaken the body guard.
- Larger backlogs now drain over multiple scheduled ticks → test continuation across cold starts, persistent rows, failures, deadlines and wraparound; document the scheduler expectations and monitor redacted aggregate counts only.
- An active stylesheet can delay first paint compared with the broken print link → avoid duplicate requests and compare font application, first paint and layout under the same conditions before and after.

## Migration Plan

1. Verify route contracts locally with synthetic payloads and mocked Sanity, SPX, Zalo and Telegram. Exercise the installed Worker runtime where possible without production requests that write data.
2. Build and verify the Next and Vinext outputs; keep the prerender allowlist/output, asset routing, preview SEO, deployed-path, API, secrets and Worker graph gates. Validate the exact built artifact with the guarded local `cf deploy --prebuilt --dry-run` path; the standalone Vinext deployment dry-run is not evidence that the prerender build ran.
3. For a separately approved release, coordinate the scheduler response change before switching versions. Rollback restores the prior Worker and prerender snapshot; roll back the scheduler expectation too. The prior Worker does not consume the private checkpoint, so no order data or cursor must be deleted on rollback.
